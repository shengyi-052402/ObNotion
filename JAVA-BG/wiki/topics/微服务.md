# 微服务

微服务架构将大型单体应用拆分为一系列小而专注的分布式服务，通过完备的注册发现、负载均衡、雪崩保护、分布式事务以及一致性治理组件，实现系统的高可用与弹性伸缩。

## 正文

### 1. 注册中心与服务治理
微服务调用需要经过服务注册、服务发现与健康检查三大核心步骤。主流实现对比：
- **Nacos**：支持 AP 与 CP 模式切换。对于临时实例采用心跳检测模式，非临时实例则由服务端主动探测；支持服务列表更新的实时**消息推送模式**，更加高效及时。
- **Eureka**：采用单纯的 AP 模式，服务提供者每 30s 发送心跳，90s 未收到心跳则从服务列表中剔除。

### 2. 远程调用与负载均衡
远程调用客户端通常集成 Ribbon 负载均衡组件：
- **Ribbon**：拉取服务列表，并利用轮询（RoundRobinRule）、加权响应时间（WeightedResponseTimeRule）、随机（RandomRule）或默认的区域敏感策略（ZoneAvoidanceRule）选择目标实例。
- **自定义策略**：可通过实现 `IRule` 接口（全局生效）或在配置文件中针对单个服务指定策略。

### 3. 服务保护与雪崩治理
服务雪崩指上游服务因下游服务瘫痪而导致自身资源耗尽、级联崩溃的现象。常用防范机制：
- **服务降级**：当被依赖服务不可用时，利用备选逻辑（Fallback）快速响应，避免阻塞线程。
- **服务熔断**：通过断路器监控请求。例如，若 10s 内请求失败率超过 50%，熔断器开启并拦截所有请求；熔断 5s 后尝试放行部分请求（Half-Open 状态）以检测服务是否恢复。
- **限流**：限制请求速率。常用**漏桶算法**（请求以恒定速率流出，起到平滑流量作用，如 Nginx）与**令牌桶算法**（桶以恒定速率产生令牌，允许突发流量获取令牌并快速处理，如 Spring Cloud Gateway 过滤限制）。

### 4. 分布式系统理论与事务
- **CAP 理论**：分布式系统在网络分区（P）发生时，无法同时满足强一致性（C）与高可用性（A）。
- **BASE 理论**：AP 方案的延伸。通过基本可用（Basically Available）、软状态（Soft state）与最终一致性（Eventually consistent）在可用与一致性间取得平衡。
- **Seata AT 模式**：通过两阶段提交（2PC）保证分布式事务的最终一致。
  - **阶段一**：RM 注册分支事务，在执行本地业务 SQL 时记录 **undo-log 快照**，随后提交本地事务。
  - **阶段二**：全局提交时，删除对应的 undo-log；全局回滚时，RM 根据 undo-log 反向恢复数据至更新前状态。

### 5. 接口幂等性设计
在分布式通信中，为避免重试引发数据重复，核心下单等接口需实现幂等性：
- **Token + Redis 方案**：
  1. 用户加载页面时，后端生成全局唯一 Token 存入 Redis（Key 为用户 ID，Value 为 Token），并将 Token 返回前端。
  2. 用户下单时携带该 Token，后端首先通过 Redis 验证 Token 存在性。若存在，执行业务并**立即删除 Token**；若不存在，直接拒绝重复请求。

### 6. 分布式任务调度
大型微服务系统中，定时任务需由分布式调度平台（如 **XXL-Job**）协调：
- **高可用执行**：配置路由策略为“故障转移”，优先把任务调度到健康的实例；设置合理的失败重试次数，并通过邮件/短信告警及时处理异常。
- **大数据量分片**：采用“分片广播”路由策略，调度中心会将分片参数广播至所有实例，各实例在执行时根据分片总数与当前分片索引进行模数取余（如 `ID % 分片总数 == 当前分片`），分摊处理大规模数据。
